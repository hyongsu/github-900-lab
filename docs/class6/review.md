# 6교시 회고

!!! abstract "이번 회고에서 할 것"
    - 팀이 겪은 구현, 검토, 변경 요청 과정을 3분 동안 돌아봅니다.
    - 오늘 남긴 기록이 실무에서 어떤 의미인지 정리합니다.

**소요 시간** 약 3분  **실습 장소** 팀 리포지토리 `lunch-picker-team<번호>`  **관련 교안** [6교시 교안](index.md#lecture)

## 회고 질문

팀원끼리 질문 하나에 한 사람씩 짧게 답합니다. 시간이 있으면 CR 이슈에 댓글로 남겨도 좋습니다.

| 번호 | 질문 | 생각해 볼 점 |
|---|---|---|
| 1 | BA가 Request changes를 했을 때, 개발자는 무엇을 보고 고쳤나요? | 말로 들은 것과 Add a suggestion으로 받은 것의 차이 |
| 2 | 자동 검사가 실패한 적이 있나요? 사람이 먼저 발견했을까요? | 쉼표 하나, `"yes"` 같은 값을 사람이 매번 찾을 수 있는지 |
| 3 | 변경 요청을 바로 고치지 않고 6단계를 거친 것이 번거로웠나요, 도움이 됐나요? | 결정 댓글과 영향 분석이 없었다면 감사 질문 1번에 답할 수 있었는지 |
| 4 | 이력 감사에서 가장 찾기 어려웠던 링크는 무엇이었나요? | Blame, 커밋, compare 중 어디에 무엇이 있는지 |
| 5 | 우리 회사 업무에서 이 흐름을 쓸 수 있는 곳은 어디인가요? | 요구사항 문서, 운영 매뉴얼, 설정 파일 변경 등 |

회고 댓글 예시입니다. 그대로 써도 되고 고쳐도 됩니다.

```markdown
## 6교시 회고 (팀<번호>)
- 잘된 점: BA의 제안을 Apply suggestion 한 번으로 반영해서 빨랐다.
- 어려웠던 점: Blame에서 Squash 병합 커밋의 작성자가 누구인지 헷갈렸다.
- 회사에서 써 보고 싶은 곳: 분기별 운영 매뉴얼 개정
```

## 강사 정리 포인트

- **리뷰 기준은 인수 조건입니다.** "좋아 보여요"가 아니라 5교시에 합의한 대표 스토리의 인수 조건 ①~④로 검토했기 때문에 Request changes에 근거가 생겼습니다. 초록 체크는 형식이 맞다는 뜻일 뿐이고, 요구 충족은 BA와 PO가 확인했습니다.
- **자동 검사는 사람을 대신하는 게 아니라 사람을 돕습니다.** 형식 실수는 Actions가 잡고, 사람은 내용이 요구와 맞는지에 집중합니다.
- **병합이 곧 배포입니다.** main에 들어간 순간 웹페이지가 바뀌었습니다. 그래서 main에 들어가기 전 검토가 중요하고, 7교시에 이 검토를 시스템으로 강제하는 분기 보호를 설정합니다.
- **변경 요청은 절차로 처리합니다.** 접수, 영향 분석, 결정, 일정 조정, 반영, 기록이 모두 이슈 댓글, PR, Release로 남았습니다.
- **증명은 링크로 합니다.** 누가 요청하고, 누가 결정하고, 누가 언제 바꾸고, 무엇이 반영됐는지를 기억이 아닌 링크로 답했습니다. 담당자가 바뀌어도 기록은 남습니다.

!!! tip "핵심"
    요구사항, 결정, 변경 이력을 한 곳에 남기면 누구나 추적할 수 있습니다.
