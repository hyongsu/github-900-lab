# 미션 6-3. 이력 감사

!!! abstract "이번 미션에서 할 것"
    - 감사 질문 5개(CR-001 관련 4개, 대표 스토리 1개)에 말이 아니라 **GitHub 링크**를 근거로 답합니다.

| 3. 개발자 PR에서 어떤 리뷰 의견이 반영됐나 | BA | PR 리뷰와 커밋 |

| 5. 대표 스토리는 누가 Must로 정했고, BA는 어떤 인수 조건으로 승인했나 | PO, BA 함께 | 대표 스토리 이슈의 PO 댓글(5교시), 대표 스토리 PR의 BA 리뷰(6교시) |

!!! note "왜 링크로 답하나요?"
    "BA가 검토했어요"라는 말은 기억에 기대지만, 링크는 누가 클릭해도 같은 화면을 보여 주는 증거입니다. 감사, 장애 원인 분석, 인수인계에서 쓰는 방식 그대로입니다.

## STEP 1. 링크 복사하는 방법 익히기 { #copy-links }

GitHub의 거의 모든 화면에는 고유 주소가 있습니다. 네 가지 복사 방법만 알면 됩니다.

**이슈나 PR의 댓글 링크**

1. 댓글 오른쪽 위 **...**(더 보기) 클릭
2. **Copy link**(링크 복사) 클릭

복사된 주소는 `https://github.com/<PO아이디>/lunch-picker-team<번호>/issues/12#issuecomment-1234567890`처럼 끝에 댓글 번호가 붙습니다. 이 주소를 열면 그 댓글로 바로 이동합니다.

**파일의 특정 줄 링크**

1. **Code** 탭에서 파일(예: `site/menus.json`)을 엽니다.
2. 왼쪽 줄 번호(예: `3`)를 클릭합니다. 줄이 노란색으로 강조됩니다.
3. 주소창의 주소를 복사합니다. 끝에 `#L3`이 붙어 있습니다.

여러 줄은 첫 줄 번호를 누르고 ++shift++를 누른 채 마지막 줄 번호를 누르면 `#L2-L4`처럼 됩니다. 줄 번호 옆 **...** → **Copy permalink**(고정 링크 복사)를 쓰면 나중에 파일이 바뀌어도 지금 그 내용을 가리키는 링크가 됩니다.

**커밋 링크**

1. History, Blame, PR의 **Commits** 탭 어디서든 커밋 메시지나 7자리 커밋 해시(예: `a1b2c3d`)를 클릭합니다.
2. 열린 커밋 화면의 주소창 주소를 복사합니다. `https://github.com/.../commit/a1b2c3d...` 형태입니다.

**비교 링크와 PR 링크**

- 비교 주소는 미션 6-2에서 연 `https://github.com/<PO아이디>/lunch-picker-team<번호>/compare/v1.0...v1.1`을 그대로 씁니다.
- PR 링크는 PR 화면 주소창 주소(`.../pull/13`)를 복사합니다.

확인: 아무 댓글 하나의 링크를 복사해 새 탭에 붙여 넣으면 그 댓글로 바로 이동합니다.

## STEP 2. 감사 질문에 답 찾기

**질문 1. 변경을 누가 요청했고, 누가 수용을 결정했나**

1. **Issues** 탭 → 위쪽 **Closed** 클릭 → `[변경요청] CR-001 배달 가능 메뉴 표시` 열기
2. 이슈 본문에서 요청자(박지은 과장)와 이슈를 만든 사람(PO)을 확인합니다.
3. PO의 `[결정]` 댓글 **...** → **Copy link**

**질문 2. menus.json의 delivery 줄은 누가, 언제, 어떤 커밋으로 바꿨나**

1. **Code** 탭 → `site` → `menus.json` 열기
2. 파일 위쪽 **Blame** 클릭. 줄마다 왼쪽에 마지막으로 바꾼 커밋, 사람, 시점이 보입니다.
3. 3번째 줄(짜장면)의 왼쪽 정보를 봅니다. 커밋 메시지 `CR-001 모든 메뉴에 배달 가능 여부(delivery) 추가`(Squash 병합이면 PR 제목)와 개발자 아이디, "N minutes ago"가 보입니다.
4. 줄 번호 `3` 클릭 → 주소창 주소 복사(끝이 `#L3`)
5. 왼쪽 커밋 메시지를 클릭해 커밋 화면을 열고 그 주소도 복사합니다.

**질문 3. 개발자 PR에서 어떤 리뷰 의견이 반영됐나**

1. **Pull requests** 탭 → **Closed** → `[CR-001] 메뉴에 배달 가능 여부 추가` 열기
2. **Conversation** 탭에서 BA의 리뷰(Approve, 제안이 있었다면 Apply suggestion 커밋)를 찾습니다.
3. PR 주소와, 반영된 리뷰 댓글의 **...** → **Copy link**를 복사합니다. 제안이 없었다면 6-1의 스토리 PR에서 Request changes와 Apply suggestion 기록을 대신 씁니다.

**질문 4. v1.0과 v1.1 사이 바뀐 파일은 몇 개인가**

1. 비교 주소 `https://github.com/<PO아이디>/lunch-picker-team<번호>/compare/v1.0...v1.1`을 엽니다.
2. 위쪽 요약의 커밋 수와 **files changed** 수를 읽습니다. 아래로 내려 파일 이름을 확인합니다.
3. 주소창 주소를 복사합니다.

**질문 5. 대표 스토리는 누가 Must로 정했고, BA는 어떤 인수 조건으로 승인했나**

5교시에 정한 것과 6교시에 확인한 것이 한 줄로 이어지는지 봅니다.

1. **Issues** 탭 → **Closed** → `[스토리] 새 메뉴 2개를 추가해 선택지 늘리기` 열기
2. 5교시 미션 5-2에서 PO가 남긴 `[PO] Must로 정했습니다.` 댓글을 찾아 **...** → **Copy link**. 작성자와 시간을 확인합니다.
3. 같은 이슈 본문의 `## 인수 조건` ①~④를 확인합니다. 본문 오른쪽 위 **edited**를 누르면 BA가 언제 인수 조건을 썼는지 수정 이력도 볼 수 있습니다.
4. 이슈 아래쪽에 연결된 PR(`[스토리 #10] 새 메뉴 2개를 추가해 선택지 늘리기`)을 클릭합니다.
5. PR **Conversation** 탭에서 BA의 **Request changes** 리뷰(어느 인수 조건이 미통과였는지)와 **Approve** 리뷰(①~④ 통과)를 찾아 각각 **...** → **Copy link**

!!! note "왜 이 질문을 하나요?"
    이슈 댓글과 Projects 값은 태그에 고정되지 않습니다. 그래서 "누가 Must로 정했나"는 이슈 댓글 링크로, "어떤 기준으로 승인했나"는 PR 리뷰 링크로 증명합니다. 같은 내용은 `v1.0` 태그에 포함된 README "MVP 범위"에도 파일로 남아 있으니, 시간이 있으면 그 링크도 함께 적습니다.

확인: 질문 5개마다 링크가 1개 이상 있습니다.

## STEP 3. CR 이슈에 감사 답변 남기기

1. CR 이슈 맨 아래 댓글 칸에 아래 템플릿을 붙여 넣고, `<...>` 부분을 찾은 내용과 링크로 바꿉니다. 각자 맡은 질문만 채워 따로 댓글을 달아도 됩니다.

    ```markdown
    ## 이력 감사 답변 (CR-001, 대표 스토리)

    **1. 누가 요청했고 누가 수용을 결정했나**
    - 요청: 경영지원팀 박지은 과장, 접수: @<PO아이디>
    - 결정: @<PO아이디> <날짜 시간>
    - 근거: <결정 댓글 링크>

    **2. menus.json의 delivery 줄은 누가 언제 어떤 커밋으로 바꿨나**
    - @<개발자아이디>, <날짜 시간>, 커밋 "<커밋 메시지>" (<커밋 해시 7자리>)
    - 근거: <menus.json #L3 줄 링크>, <커밋 링크>

    **3. 개발자 PR에서 어떤 리뷰 의견이 반영됐나**
    - 리뷰어 @<BA아이디>: "<리뷰 의견 요약>" → <반영 방법: Apply suggestion 등>
    - 근거: <PR 링크>, <리뷰 댓글 링크>

    **4. v1.0과 v1.1 사이 바뀐 파일 수**
    - <N>개 (<파일 이름들>), 커밋 <M>개
    - 근거: <compare 링크>

    **5. 대표 스토리는 누가 Must로 정했고, BA는 어떤 인수 조건으로 승인했나**
    - Must 결정: @<PO아이디> <날짜 시간> (5교시), 이유: "<PO 댓글 요약>"
    - 인수 조건: ① 카드 8개 ② 새 메뉴 종류, 가격, 거리와 비빔밥 "혼밥 가능" ③ 예산 10000에 마라탕 보임 ④ 자동 검사 초록 체크
    - 수정 요청: @<BA아이디> "<미통과였던 인수 조건과 이유>" → <반영 방법: Apply suggestion 등>
    - 승인: @<BA아이디> <날짜 시간> (6교시), PO 화면 확인: <PO 확인 댓글 링크>
    - 근거: <PO Must 댓글 링크>, <대표 스토리 PR 링크>, <BA Approve 리뷰 링크>
    ```

2. **Comment** 클릭
3. 다른 팀원이 링크를 하나씩 눌러 정말 그 화면이 열리는지 확인합니다.

확인: CR 이슈에 감사 답변 댓글이 있고, 모든 링크가 열립니다.

## 도전. 옆 팀 리포지토리에 Fork로 기여하기

시간이 남는 팀만 합니다. 옆 팀 리포지토리에는 쓰기 권한이 없으므로 분기를 직접 만들 수 없습니다. 이럴 때 **Fork**(내 계정으로 연결된 사본 만들기)를 씁니다. 원리는 [7교시 교안의 Fork](../class7/index.md#fork)에서 다시 설명합니다.

1. 옆 팀 리포지토리 `https://github.com/<옆팀PO아이디>/lunch-picker-team<옆팀번호>`를 엽니다.
2. 오른쪽 위 **Fork** 클릭 → Owner(소유자)가 내 아이디인지 확인 → **Create fork**(Fork 만들기) 클릭
3. 내 계정에 `<내아이디>/lunch-picker-team<옆팀번호>`가 생깁니다. 이름 아래 `forked from ...`이 보입니다.
4. 이 사본에서 `site/menus.json` → 연필 아이콘 → 마지막 메뉴 줄 끝에 쉼표를 붙이고 그 아래 한 줄 추가. `delivery`가 있는 팀이면 같이 넣습니다.

    ```json
      { "name": "제육덮밥", "category": "한식", "price": 8500, "distance": 300, "solo": true, "delivery": true }
    ```

5. **Commit changes...** → 메시지 `옆 팀 제안: 제육덮밥 메뉴 추가` → **Commit changes**
6. 위쪽 **Contribute**(기여하기) 클릭 → **Open pull request** 클릭
7. 위쪽 비교 줄에서 **base repository**가 옆 팀의 원래 리포지토리(`<옆팀PO아이디>/lunch-picker-team<옆팀번호>`), base가 `main`인지 확인합니다.
8. 제목과 본문 입력 → **Create pull request**

    ```markdown
    팀<내팀번호>에서 제안합니다. 회사 근처 제육덮밥집을 메뉴에 추가하면 좋겠습니다.
    ```

9. 옆 팀에 알려 줍니다. 옆 팀은 자기 리포지토리 **Pull requests**에서 이 PR을 보고 리뷰할 수 있습니다.

확인: 옆 팀 리포지토리의 **Pull requests**에 내 PR이 보입니다.

## 막히면

??? failure "Blame에서 delivery 줄의 커밋이 개발자가 아니라 PM으로 나와요"
    Squash and merge로 병합하면 main에 새로 생긴 커밋의 작성자는 원래 개발자로, 병합한 사람(PM)은 committer로 남습니다. 화면에 두 사람이 함께 보일 수 있습니다. 커밋을 클릭하면 `<개발자> authored and <PM> committed`처럼 나옵니다. 둘 다 답에 적으면 됩니다.

??? failure "댓글에 ... 메뉴가 안 보여요"
    댓글 상자 오른쪽 위에 마우스를 올려야 나타납니다. 또는 댓글 위쪽 시간 표시("5 minutes ago")를 클릭하면 주소창에 그 댓글 주소가 들어갑니다.

??? failure "줄 번호를 눌러도 주소에 #L이 안 붙어요"
    **Blame** 화면이 아니라 일반 파일 화면(**Code**)에서 해 보세요. 화면이 넓은 미리 보기 모드라면 **Code** 버튼을 눌러 원문 보기로 바꿉니다.

??? failure "Fork 버튼을 눌렀는데 이미 있다고 나와요"
    전에 같은 리포지토리를 Fork한 적이 있으면 기존 사본으로 이동합니다. 그 사본을 그대로 쓰면 됩니다.

??? failure "Contribute 메뉴에 Open pull request가 회색이에요"
    사본에 아직 커밋이 없거나 원본과 내용이 같다는 뜻입니다. 사본의 `main`에 커밋이 들어갔는지 확인하세요.
