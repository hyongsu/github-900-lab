# 용어집

이 과정에 나오는 용어를 가나다순이 아니라 **배우는 순서대로** 모았습니다.

## 1교시

| 용어 | 뜻 |
|---|---|
| 버전 관리 | 파일이 언제, 누구에 의해, 왜 바뀌었는지 기록하고 이전 상태로 돌아갈 수 있게 하는 일 |
| Git | 버전 기록을 저장하는 프로그램. 내 컴퓨터에서도 동작한다 |
| GitHub | Git 리포지토리를 인터넷에 보관하고 협업 기능(이슈, 리뷰, 프로젝트 관리)을 더한 서비스 |
| 리포지토리 (Repository) | 프로젝트 폴더. 파일과 그 파일의 모든 변경 기록이 함께 들어 있다 |
| 커밋 (Commit) | 저장 기록 한 건. 작성자, 시간, 메시지, 그 순간의 스냅샷, 앞 커밋 번호가 들어 있다 |
| 스냅샷 | 커밋 순간 프로젝트 전체의 모습. 바뀐 파일만 새로 저장하고 나머지는 이전 것을 가리킨다 |
| 해시 (커밋 번호) | 커밋 내용으로 계산한 고유 번호. 보통 앞 7자리만 쓴다. 예: `a1b2c3d` |
| 이력 (History) | 커밋을 시간 순서로 모은 목록 |
| 로컬 리포지토리 | 내 컴퓨터에 있는 리포지토리 |
| 원격 리포지토리 | GitHub에 있는 리포지토리 |
| 템플릿 (Template) | 다른 리포지토리를 만들 때 출발점이 되는 리포지토리. 복사본은 원본과 연결되지 않는다 |
| GitHub Pages | 리포지토리의 파일을 웹페이지로 공개하는 기능 |

## 2교시

| 용어 | 뜻 |
|---|---|
| README | 리포지토리 첫 화면에 보이는 소개 문서 |
| Markdown | `#`, `**`, `-` 같은 기호로 문서 모양을 만드는 형식 |
| 이슈 (Issue) | 할 일, 요구사항, 질문, 버그를 담는 카드. 댓글 대화가 기록으로 남는다 |
| 라벨 (Label) | 이슈의 종류나 우선순위를 표시하는 꼬리표 |
| 담당자 (Assignee) | 이슈를 맡은 사람 |
| 마일스톤 (Milestone) | 함께 내보낼 이슈 묶음. 진행률이 자동 계산된다 |
| 이슈 템플릿 | 새 이슈를 열 때 미리 채워지는 양식 |
| 에픽 (Epic) | 여러 작은 요구로 쪼개야 하는 큰 요구 |
| 하위 이슈 (Sub-issue) | 큰 이슈를 쪼갠 작은 이슈 |
| 멘션 (@아이디) | 댓글에서 사람을 불러 알림을 보내는 기능 |

## 3교시

| 용어 | 뜻 |
|---|---|
| 분기 (Branch) | 원본에 영향 없이 따로 작업하는 갈래. 실제로는 커밋을 가리키는 이름표 |
| main | 기본 분기. 원본 역할을 한다 |
| GitHub flow | 분기 → 커밋 → PR → 리뷰 → 병합으로 변경을 반영하는 흐름 |
| Pull Request (PR) | "내 분기의 변경을 원본에 반영해 주세요"라는 제안서 |
| compare / base | PR에서 내가 고친 분기 / 합칠 대상 분기 |
| 리뷰 (Review) | PR을 검토하고 Comment, Request changes, Approve 중 하나로 답하는 일 |
| 변경 제안 (Suggestion) | 리뷰어가 고친 문장을 직접 제안하고, 작성자가 버튼 한 번으로 반영하는 기능 |
| 병합 (Merge) | 분기의 변경을 다른 분기에 합치는 일. merge, squash, rebase 세 방식이 있다 |
| 충돌 (Conflict) | 같은 파일의 같은 줄을 서로 다르게 고쳐서 Git이 스스로 합칠 수 없는 상태 |
| revert | 커밋을 지우지 않고 그 커밋을 취소하는 새 커밋을 추가하는 되돌리기 |
| reset | 커밋 기록 자체를 지우는 되돌리기. 함께 쓰는 리포지토리에서는 위험하다 |
| Blame | 파일의 줄마다 마지막으로 바꾼 사람과 커밋을 보여 주는 화면 |

## 4~6교시

| 용어 | 뜻 |
|---|---|
| Projects | 이슈를 표, 보드, 로드맵으로 모아 보는 기획판 |
| 필드 (Field) | Projects에서 직접 만드는 항목. 단일 선택, 반복, 숫자, 날짜 등 |
| 스프린트 (Iteration) | 정해진 기간(예: 1주) 단위의 작업 묶음 |
| MoSCoW | Must, Should, Could, Won't로 우선순위를 나누는 기법 |
| MVP | 가치를 확인할 수 있는 가장 작은 출시 범위. Must만 모은 것 |
| PO | 제품 책임자. 무엇을 왜 만들지 정하고 최종 승인한다 |
| PM | 프로젝트 관리자. 언제 누가 할지 정하고 진행을 관리한다 |
| BA | 업무 분석가. 요구를 구체적인 요구사항으로 만들고 충족 여부를 검토한다 |
| 사용자 스토리 | "[누구]로서, [무엇]을 하고 싶다. 왜냐하면 [이유]" 형식의 요구사항 |
| 인수 조건 | 스토리가 완성됐다고 판단하는 기준. Given-When-Then 형식 |
| Release, 태그 | 특정 시점에 v1.0 같은 이름을 붙여 남기는 기능. 기준선으로 쓴다 |
| GitHub Actions | "이런 일이 생기면 이 작업을 해라"를 자동으로 실행하는 기능 |
| 워크플로 파일 | Actions의 내용을 적은 파일. `.github/workflows/` 폴더에 있다 |
| 변경 요청 (CR) | 확정된 요구사항을 바꿔 달라는 요청 |

## 7교시

| 용어 | 뜻 |
|---|---|
| clone | 원격 리포지토리를 내 컴퓨터로 복제하는 명령 |
| 스테이징 (add) | 이번에 커밋할 파일만 골라 담아 두는 단계 |
| push / pull | 내 커밋을 GitHub에 올리기 / GitHub의 새 커밋을 내려받기 |
| Codespaces | 브라우저에서 바로 여는 개발 환경. 터미널을 쓸 수 있다 |
| Fork | 권한이 없는 리포지토리를 원본과 연결된 사본으로 복사하는 기능. 원본에 PR을 보낼 수 있다 |
| PAT | 개인 접근 토큰. 비밀번호 대신 쓰는 열쇠 |
| SSH 키 | 내 컴퓨터를 GitHub에 등록하는 인증서 |
| 2FA | 2단계 인증. 비밀번호에 휴대폰 코드를 더한다 |
| SAML SSO | 회사 계정으로 GitHub에 로그인하는 방식 |
| 분기 보호 (Ruleset) | main 같은 분기에 "PR 필수, 승인 필수" 같은 규칙을 거는 기능 |
| CODEOWNERS | 경로마다 승인 책임자를 정하는 파일 |
| .gitignore | Git이 무시할 파일 목록. 비밀번호 파일 등을 실수로 올리지 않게 한다 |
