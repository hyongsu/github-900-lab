# 5교시 회고

!!! abstract "이번 회고에서 할 것"
    - 요구를 주고받으며 느낀 점을 팀 안에서 나눕니다.
    - 이슈, 멘션, Projects, Release가 실제 업무에서 어떤 의미인지 정리합니다.
    - 6교시에 이어서 쓸 것을 확인합니다.

**소요 시간** 약 5분  **실습 장소** 팀 리포지토리 `lunch-picker-team<번호>`  **관련 교안** [5교시 교안](index.md#lecture)

## 팀 회고 질문

팀원끼리 한 사람씩 짧게 답해 봅니다. 질문 하나에 1분이 넘지 않게 합니다. 정답은 없습니다.

1. **요구를 주고받으며 가장 막혔던 순간은 언제였나요?** 무엇을 기다리고 있었고, 누구에게 무엇을 물어야 했나요?
2. **질문을 이슈 댓글로 남긴 것이 메신저로 묻는 것보다 나았던 점은 무엇인가요?** 반대로 불편했던 점은요?
3. **Must를 3개로 고르기가 왜 어려웠나요?** 무엇을 기준으로 줄였나요?
4. **BA가 스스로 정하지 못하고 PO에게 넘긴 질문은 무엇이었나요?** 그 질문은 누가 정하는 것이 맞았나요?
5. **내 역할이 평소 업무와 비슷했나요, 달랐나요?** 다른 역할을 해 보니 그 역할에 대해 새로 알게 된 것은 무엇인가요?

팀에서 나온 이야기 중 기억하고 싶은 것을 팀 리포지토리에 남겨 두고 싶다면, 에픽 하나에 댓글로 적어도 좋습니다.

```text
[5교시 회고] 
- 막혔던 점: 
- 좋았던 점: 
- 다음에 바꿀 점: 
```

## 강사 정리 포인트

!!! tip "기록이 곧 근거입니다"
    오늘 주고받은 질문, 답, 결정은 모두 이슈 댓글로 남았습니다. 메신저 대화는 시간이 지나면 찾기 어렵고, 새로 온 사람은 볼 수 없습니다. 이슈 댓글은 요구사항 바로 옆에 남아, 6교시 이력 감사에서 "왜 이렇게 만들었는지"의 근거가 됩니다.

!!! tip "애매한 요구는 짐작하지 않고 묻습니다"
    개발자의 질문 하나가 회의록에서 결론 나지 않은 충돌을 드러냈습니다. 질문이 없었다면 개발자가 짐작으로 만들고, 검토 단계에서야 문제가 드러났을 것입니다. 요구사항 단계에서 고치는 비용이 가장 적습니다.

!!! tip "결정할 사람이 결정합니다"
    BA는 구체화하고, 정할 수 없는 것은 PO에게 넘겼습니다. `확인 필요` 라벨과 `@PO` 멘션은 "이건 내가 정할 일이 아니다"를 분명히 하는 도구입니다. 요청자끼리 의견이 다를 때는 제품 책임자가 목적과 범위를 기준으로 결정하고, 이유를 남깁니다.

!!! tip "Must가 적어야 MVP입니다"
    Must를 줄이는 것은 요구를 버리는 것이 아니라 순서를 정하는 것입니다. Won't로 남긴 투표 스토리는 닫지 않고 그대로 있어서, 2차 출시 때 다시 꺼내 볼 수 있습니다.

!!! tip "v1.0은 합의의 증거입니다"
    Release `v1.0`은 "이 시점의 요구사항에 팀이 합의했다"는 이름표입니다. 이제부터 들어오는 새 요구는 기준선과 비교되는 **변경 요청**입니다. 기준선이 없으면 무엇이 바뀌었는지조차 말할 수 없습니다.

## 다음 교시 예고

6교시 **팀 실습 ② 구현, 검토, 변경**에서는 MVP를 처음부터 만들지 않습니다. 기본 화면(메뉴 카드, 예산 칸, 거리 칸, "아무거나 골라 줘" 버튼)은 Starter에 이미 있고, 6교시에는 팀이 합의한 변경 1건(대표 스토리)을 협업 절차로 반영합니다.

| 오늘 만든 것 | 6교시에 쓰는 곳 |
|---|---|
| 대표 스토리 `[스토리] 새 메뉴 2개를 추가해 선택지 늘리기` | 개발자가 `story-<이슈번호>` 분기(예: `story-10`)에서 메뉴 2개를 추가하고 PR을 올립니다. 나머지 Must 두 개는 Starter에 이미 있어 확인만 합니다 |
| 대표 스토리의 인수 조건 ①~④ | BA가 PR을 검토하는 기준이 됩니다. **Request changes**도 한 번 써 봅니다. PO는 배포된 웹페이지에서 ①~③을 직접 확인합니다 |
| `진행 보드` | PM이 대표 스토리를 In Progress로 옮기고, PR이 병합되면 카드가 자동으로 Done으로 갑니다 |
| `v1.0` | 강사(현업 고객)가 던지는 변경 요청 CR-001을 반영한 뒤 `v1.1`과 비교합니다 |

쉬는 시간이 끝나면 PR을 열면 자동으로 돌아가는 검사, GitHub Actions의 원리부터 봅니다. 이번 교시가 끝나면 우리 팀 웹페이지에 실제로 바뀐 내용이 반영되는 것을 볼 수 있습니다.
